# سجل بوابة المجبل

تطبيق ويب داخلي لتسجيل حركة الآليات من وإلى المجبل، مع تقارير المدة والمسافة
والتنبيهات. يعمل على سيرفر الشركة داخل الشبكة المحلية، وبياناته في
**SQL Server** (أو MongoDB أو SQLite — يُختار بسطر واحد).

---

## التشغيل السريع

يحتاج **Node.js 24 LTS** و**SQL Server 2016** أو أحدث (نسخة Express تكفي).

انسخ `gatelog.config.example.json` باسم `gatelog.config.json` واملأ بيانات
الاتصال، ثم:

```bash
npm install
```

```bash
node server.js
```

ثم افتح <http://localhost:8787>

عند **أول تشغيل فقط** يطبع الخادم كلمتَي مرور عشوائيتين — واحدة للبوابة وأخرى
للمدير — ويحفظهما أيضًا في `data\كلمات-المرور-الأولية.txt`.
غيّرهما من تبويب «الإعدادات» ثم احذف الملف.

---

## اليوم الأول

النظام يبدأ من قاعدة فارغة. الترتيب التالي يهمّ:

**1. غيّر كلمتَي المرور** من تبويب «الإعدادات»، ثم احذف ملف كلمات المرور
الأولية، وأبلغ الحرّاس بكلمة مرور البوابة وحدها.

**2. سجّل كل الآليات مع كيلومتراجها الحالي** من تبويب «الآليات».

هذه الخطوة تستحق دقة، ولها سبب حسابي واحد:

> مسافة أول رحلة لكل آلية = كيلومتراج العودة − **كيلومتراج البداية المُسجَّل هنا**.
> الرحلات التالية تُحسب من قراءة الرحلة السابقة، فلا تتأثر.

أي أن رقم بداية خاطئ يُفسد **رحلة واحدة فقط** لتلك الآلية، ثم يصحّح النظام
نفسه. ومع ذلك، اقرأ العدّاد من الآلية نفسها لا من الذاكرة.

### عند استبدال العدّاد أو دورانه

العدّاد لا ينقص. حين تكون قراءة العودة **أقل** من القراءة السابقة، تنكسر
سلسلة الحساب: لا سبيل لمعرفة مسافة تلك الرحلة، لأن القراءة الأخيرة للعدّاد
القديم غير معلومة.

في هذه الحالة يعرض النظام **«العدّاد أقل من السابق»** بدل رقم:

| التاريخ | قراءة العدّاد | المسافة |
|---|---|---|
| 2026-08-28 | 100,150 | 150 كم |
| 2026-08-29 | 500 ← عدّاد مستبدل | العدّاد أقل من السابق |
| 2026-08-30 | 640 | 140 كم |

إجمالي الآلية = 290 كم — الرحلة المجهولة تُستثنى ولا تُحتسب صفرًا ولا سالبًا.
والرحلات التالية تُحسب طبيعيًا من القراءة الجديدة، فتصلح السلسلة نفسها.

> هذا ليس تفصيلًا تجميليًا: قبل هذا التصحيح كان طرح القراءتين يُخرج
> **−99,650 كم**، فيقلب إجمالي الآلية إلى سالب ويولّد تنبيه «تجاوز مسافة»
> **كاذبًا على الرحلات الصحيحة** لأن المتوسط ينهار.

يبقى الخيار الأنظف عند استبدال عدّاد: أن يحدّث المدير كيلومتراج الآلية من
تبويب «الآليات» ليعكس القراءة الجديدة.

آلية غير مسجّلة **لا تستطيع** الخروج: الخادم يرفض المغادرة برسالة صريحة
للحارس. هذا مقصود — رحلة بلا كيلومتراج بداية تعني مسافة غير قابلة للحساب أبدًا.

**3. لا تحتاج تسجيل السائقين ولا الزبائن مسبقًا.** يكتبهما الحارس بحرية، وبعد
أول مرة يظهران في قائمة الاقتراحات تلقائيًا، فلا يُعاد كتابتهما.

**4. شغّل النظام يومًا واحدًا بالتوازي مع الطريقة الورقية** لا بديلًا عنها.
هذا اليوم يكشف ما لا يكشفه أي اختبار برمجي: آلية نُسي تسجيلها، أو حارس يكتب
رقم الآلية بصيغة مختلفة عمّا سجّله المدير.

## قاعدة البيانات

ثلاثة محرّكات خلف واجهة واحدة، تُختار من `driver` في ملف الإعدادات.
المحرّكات الثلاثة تجتاز **نفس مجموعات الاختبار**:

| المحرّك | متى تختاره |
|---|---|
| `mssql` (الافتراضي) | يوجد SQL Server على سيرفر الشركة — أسرع مسار للموافقة والتشغيل |
| `mongo` | MongoDB محلية أو Atlas السحابية |
| `sqlite` | لا يمكن تثبيت أي خادم قواعد بيانات — ملف واحد، بلا أي طلب من الـ IT |

```json
{ "driver": "mssql" }
```

التفاصيل الكاملة لكل محرّك:
[SQL Server](deploy/SQLSERVER-SETUP.md) · [Atlas](deploy/ATLAS-SETUP.md)

### البنية

قاعدة باسم `gate_log` بستّة جداول (أو مجموعات في MongoDB):

| المجموعة | المحتوى |
|---|---|
| `vehicles` | الآليات المسجّلة وكيلومتراج البداية |
| `entries` | كل عملية خروج/دخول |
| `settings` | كلمتا المرور (مُجزّأتين) |
| `sessions` | الجلسات النشطة، تُحذف تلقائيًا بفهرس TTL |
| `login_attempts` | عدّاد المحاولات الفاشلة لكل جهاز |
| `audit` | سجل التدقيق |

قراران تصميميان يستحقان الانتباه:

- **المعرّفات نصوص من توليدنا** (`_id` نصّي) لا `ObjectId`. خلط أنواع المعرّفات
  هو نفس العلّة التي كانت تُنتج صفوفًا مكررة في نسخة Google Sheets.
- **التواريخ والأوقات نصوص** بصيغة `YYYY-MM-DD` و`HH:MM`، ولا تُخزَّن أبدًا
  كنوع `Date`. هذا يلغي انزياح التوقيت الذي كان يفسد كل حسابات المدة.

### فهرسان يفرضان قواعد العمل في قاعدة البيانات نفسها

القاعدتان مفروضتان في قاعدة البيانات لا في الكود، وبنفس الأثر في المحرّكات الثلاثة:

| القاعدة | SQL Server | MongoDB | SQLite |
|---|---|---|---|
| لا آليتان بنفس الاسم | فهرس فريد | فهرس فريد | فهرس فريد |
| رحلة مفتوحة واحدة لكل آلية | فهرس مُرشَّح | فهرس جزئي | فهرس جزئي |

```sql
-- SQL Server
CREATE UNIQUE INDEX ux_one_open_trip ON dbo.entries(vehicle) WHERE status = N'out';
```

الفهرس الثاني هو ما يمنع فعليًا خروج آلية هي أصلًا في الخارج حين يرسل جهازان
على البوابة الطلب في نفس اللحظة — لا يكفي الفحص في الكود وحده، وقد أثبت
`test/concurrency.test.js` ذلك بطلبات متزامنة حقيقية.

### تبديل المحرّك

سطر واحد في `gatelog.config.json`، أو متغيّر بيئة لتجربة سريعة:

```bash
GATE_LOG_DB=sqlite node server.js
```

SQLite لا يحتاج أي خادم قواعد بيانات ولا أي طلب من الـ IT — مفيد للتجربة على
جهاز محلي، أو كخطة بديلة إن تعذّر الوصول إلى SQL Server.

### MongoDB Atlas السحابية

مدعومة بلا تعديل على الكود — يكفي وضع رابط `mongodb+srv://` في الإعدادات.
التطبيق يكتشف الاتصال السحابي تلقائيًا ويطيل مهل الانتظار ويفعّل ضغط البيانات
وإعادة المحاولة عند الانقطاع العابر.

**قبل أن تختار Atlas اقرأ [deploy/ATLAS-SETUP.md](deploy/ATLAS-SETUP.md)** — فيه
الخطوات كاملة، ومقارنة صريحة لما تكسبه وما تخسره. أهم ما تخسره: انقطاع
الإنترنت يوقف تسجيل الشاحنات على البوابة.

| | حساب البوابة | حساب المدير |
|---|---|---|
| كلمة مرور | ✅ مطلوبة | ✅ مطلوبة |
| تسجيل مغادرة | ✅ | ❌ لا يرى التبويب |
| تسجيل عودة | ✅ | ❌ |
| البحث في الآليات الخارجة | ✅ | — |
| إدارة الآليات | ❌ | ✅ |
| السجل الكامل والبحث فيه | ❌ | ✅ |
| تعديل / حذف عملية | ❌ | ✅ |
| التقارير والتنبيهات | ❌ | ✅ |
| تصدير Excel | ❌ | ✅ |
| تغيير كلمات المرور | ❌ | ✅ |
| سجل التدقيق | ❌ | ✅ |

الصلاحيات مفروضة **في الخادم**. إخفاء زر في الواجهة ليس حماية — أي شخص يستطيع
استدعاء الواجهة البرمجية مباشرة، والخادم هو من يرفض.

### دور «منسق حركة الآليات» وصلاحية «تعديل السجل الكامل»

دور جديد `fleet_coordinator`، وله **حساب جاهز** اسمه `منسق_حركة_الاليات` (الاسم الكامل «منسق حركة الآليات»):
يُنشأ مع الحسابات الافتراضية عند التثبيت الأول، وفي **قاعدة قائمة** يُزرع تلقائيًا مرة واحدة عند أول إقلاع بعد الترقية
إن لم يوجد أي مستخدم بهذا الدور ولا بهذا الاسم، بكلمة مرور عشوائية تُطبع في نافذة الخادم وتُضاف إلى ملف
`كلمات-المرور-الأولية.txt` في مجلد البيانات (دون المساس بما فيه ولا بأي حساب آخر). غيّر كلمة المرور بعد أول دخول من
تبويب «المستخدمون». ويمكن للأدمن إنشاء حسابات منسقين إضافية من قائمة الأدوار في التبويب نفسه. يمتلك **صلاحيات مدير الآليات
الحالية** — تبويبات الآليات والسائقين والسجل الكامل والتقارير والتنبيهات وتصدير CSV — عدا ما يختص به المدير وحده (أدناه)، وبقية
الأدوار بلا أي تغيير.

الصلاحيتان اللتان يختص بهما مدير الآليات (`fleet_manager`) دون المنسق: **تعديل السجل الكامل** — تعديل العملية
بكل حقولها بعد حفظها (`PUT /api/entries/:id`) — و**حذف العملية** (`DELETE /api/entries/:id`). الخادم يرفض غير المدير بـ403 ولا يكفي إخفاء الزر. كل تعديل يُسجَّل في
سجل التدقيق (`edit_entry`) مع المستخدم والدور والوقت والسجل قبل التعديل وبعده. الصلاحيات معرَّفة في موضع واحد
في `server.js` (`FLEET_ROLES` و`EDIT_FULL_RECORD_ROLES` و`DELETE_ENTRY_ROLES`) ضمن نظام الأدوار نفسه، والواجهة تقرأ `permissions` من `/api/state`.

تحسينان على التعديل نفسه: لم تعد ملاحظة العودة تضيع عند تعديل عملية غير مكتملة، ومحاولة إبقاء سجل «في الخارج» لآلية
لها رحلة مفتوحة أخرى تعيد رسالة 409 واضحة بدل خطأ خادم.

**قاعدة البيانات (SQL Server فقط):** عمودا الدور في `sessions` و`audit` كانا `NVARCHAR(16)` وأسماء الأدوار
`fuel_warehouse_manager` و`fleet_coordinator` أطول من ذلك. التوسيع إلى 32 حرفًا (دون لمس أي بيانات) في
`migrations/001-widen-role-columns.sql`، ويُنفَّذ أيضًا تلقائيًا عند إقلاع الخادم، فلا تأخير إن شُغِّل الملف يدويًا.
SQLite وMongoDB لا يحتاجان أي migration.

## إحصاءات الزبائن والضيوف في لوحة الأدمن

بطاقتان في أعلى لوحة **الأدمن**: «عدد الزبائن» و«عدد الضيوف» (الرقم الكبير = الإجمالي، وتحته «اليوم التشغيلي: n»).
الأرقام تُحسب بـ `COUNT … GROUP BY` من جدول `guest_visits` الفعلي لكل حسابات البوابة معًا (لا نافذة أيام، ولا يتأثر العدّ
بمن سجّل أو بخروج الزيارة)، وتصل مع `/api/state` للأدمن وحده (`guestStats`؛ `null` لبقية الأدوار) فتتحدّث بالاستطلاع الدوري
(8 ثوانٍ) دون إعادة تحميل. لا جدول جديد: أُضيف إلى `guest_visits` عمود `visit_type` (`customer` | `guest`، الافتراضي `guest`).
وقت التسجيل محفوظ أصلًا (`date_in`/`time_in`). نموذج «تسجيل دخول ضيف» في البوابة يحصل على خيار «نوع الزيارة».

**Migration يدوي (لا يُطبَّق تلقائيًا):** `migrations/002-add-guest-visit-type.sql` على SQL Server. قبل تطبيقه يعمل كل شيء كما كان:
الكل يُحتسب «ضيوفًا»، «عدد الزبائن» = 0، ولا يظهر خيار «زبون» في البوابة، ويرفض الخادم تسجيل «زبون» (409) بدل أن يسجّله ضيفًا بصمت.
بعد تطبيقه يلتقط التطبيق العمود خلال 30 ثانية دون إعادة تشغيل. القواعد الجديدة (من الصفر) تنشئ العمود مع الجدول؛ MongoDB لا يحتاج شيئًا.
الاختبار: `node test/guest-stats.test.js`.

## سير العمل

**على البوابة** — تبويب واحد فقط: «تسجيل عملية»

1. عند خروج آلية: اختر الآلية والسائق والزبون ووقت المغادرة → «تسجيل المغادرة».
   نموذج المغادرة لا يحتوي حقول عودة إطلاقًا، لأن العودة تحدث لاحقًا.
2. عند عودتها: ابحث عنها في قائمة «آليات في الخارج» → «تسجيل العودة» → أدخل
   الكيلومتراج → «تأكيد العودة».

**البحث** يقبل رقم الآلية أو اسم السائق أو الزبون، ويطابق:

- الأرقام العربية والهندية معًا — كتابة `٣٠` تجد `قلاب رقم 30`
- الاختلافات الإملائية الشائعة — `احمد` تجد `أحمد`
- عدة كلمات معًا — `احمد اسمنت` تجد رحلات أحمد إلى معمل الإسمنت

قائمة الخارج **لا** تُبحث بالتاريخ عمدًا: كل ما فيها خارج الآن، وإدراج التاريخ
كان يجعل البحث عن «30» يطابق كل عمليات يوم 30 من الشهر.
في السجل الكامل البحث بالتاريخ يعمل، لكن فقط حين يبدو الطلب تاريخًا
(`2026-08` مثلًا) لا رقمًا مجرّدًا.

**عند المدير** — لا يوجد تبويب «تسجيل عملية». التصحيح يتم من «السجل الكامل» عبر
زر «تعديل» الذي يفتح نافذة فيها كل الحقول بما فيها بيانات العودة.

## اليوم التشغيلي (03:00 فجرًا)

لوحة التحكم تعرض أرقام **اليوم التشغيلي الحالي** لا أرقامًا تراكمية. اليوم التشغيلي
يبدأ الساعة **03:00 فجرًا** وينتهي **02:59:59** من اليوم التالي. عند 03:00 تتصفّر
الأرقام اليومية على الشاشة المفتوحة تلقائيًا دون تحديث الصفحة.

| البطاقة | كيف تُحسب |
|---|---|
| عمليات اليوم التشغيلي | الرحلات التي **غادرت** خلال اليوم التشغيلي (مغادرة 01:30 تنتمي ليوم أمس) |
| عداد الزبائن اليومي | الزبائن المميّزون في عمليات اليوم التشغيلي |
| تنبيهات نشطة اليوم التشغيلي | الرحلات المتجاوزة التي **عادت** خلال اليوم التشغيلي (التنبيه لا ينشأ إلا عند العودة) |
| إجمالي الآليات في الخارج الآن (جملة في الزاوية السفلية للوحة) | الآليات التي لها مغادرة بلا عودة، كل آلية مرة واحدة مهما كان يوم خروجها |
| الجبالات / سيارات الخدمة / السيلوهات / المضخات | نفس العدّاد السابق مقسّمًا حسب `type` الآلية (الخارج/المسجّل) |

- **لا يُعدَّل أي سجل ولا أي جدول.** اليوم التشغيلي يُشتق وقت العرض من `dateKey` و`departTime`
  المخزّنين، فيسري بأثر رجعي على كل السجلات القديمة، والسجل الكامل يعرض كل الأيام.
- رحلة تبدأ قبل 03:00 وتنتهي بعدها تُحتسب عملية واحدة في يوم مغادرتها، وتنبيهها (إن وُجد)
  في يوم عودتها، وتبقى في «الخارج الآن» حتى تُسجَّل عودتها.
- التقارير (الدورية والشهرية والموارد البشرية وتقرير المضخات) تجمّع حسب اليوم التشغيلي أيضًا.
  وحدة المازوت (تقرير المخزون وتصالح العدّادات) باقية على التاريخ الميلادي.
- **آلية بلا نوع مسجّل** (آليات قديمة سُجّلت قبل إضافة الأنواع) تدخل في «إجمالي الخارج الآن»
  وتظهر في بطاقة «بلا نوع مسجّل» ولا يُفترض لها نوع. صنّفها من تبويب «الآليات».
- لتغيير ساعة البداية: `dayStartHour` في `gatelog.config.json` أو `GATE_LOG_DAY_START_HOUR` (0–23).

## التقارير والتنبيهات (تبويبات مستقلة)

تبويب «التقارير والتنبيهات» (للأدمن ومدير الآليات) مقسّم إلى تبويبات فرعية، **كلٌّ بفلاتره**، بهذا الترتيب:

1. تقرير المضخات – كمية الضخ (مطابقة باسم الزبون)
2. التقرير الدوري – الزبائن وكميات الصب
3. التقرير الدوري – السائقون
4. التقرير الدوري – الآليات
5. التقرير الدوري – استهلاك المازوت مقابل الكيلومترات
6. تقرير الآليات
7. التنبيهات (تبويب مستقل)

وبعدها ثلاثة تقارير كانت موجودة سابقًا وبقيت كتبويبات إضافية (حدودها منقّطة): تقرير الزبائن – مقارنة الآليات،
تقرير السائقين، مقارنة كيلومترات البوابة والمازوت.

**تحميل البيانات.** عند فتح أي تبويب تُقرأ بيانات **اليوم التشغيلي الحالي** من قاعدة البيانات وحدها
(`GET /api/reports/period?from=&to=`)، لا كل بيانات النظام. تتغيّر الفترة من قائمة «الفترة»:
اليوم الحالي (الافتراضي) · أمس · آخر 7 أيام · آخر 30 يومًا · يوم محدد · من–إلى. تغيير الفترة يعيد القراءة
من قاعدة البيانات، والبحث النصي يُطبَّق على بيانات الفترة المحمّلة فورًا. الفترة التي تضم اليوم الحالي
تتجدد تلقائيًا كل نحو 30 ثانية، وتتبدّل عند 03:00 دون تحديث الصفحة.

**الفلاتر** (تجتمع معًا): الفترة + اسم الزبون (تقارير الزبائن والمضخات والتنبيهات) + اسم السائق (تقارير السائقين)
+ رقم/اسم الآلية (تقارير الآليات والمازوت والمضخات والتنبيهات والمقارنة) + نوع التنبيه (وقت/مسافة) + التجميع
(تلقائي/يومي/شهري للجداول الدورية). الأزرار: «بحث / تطبيق» و«مسح الفلاتر» (يعيد اليوم الحالي ويفرّغ الحقول) و«تحديث».
كل تبويب يحتفظ بفلاتره عند التنقل بين التبويبات، ويعيد قراءة بياناته عند الدخول إليه.

**اليوم التشغيلي (03:00)** مطبّق بالطريقة نفسها على كل التقارير والتنبيهات حتى عند اختيار يوم سابق:
الرحلة تتبع يوم **مغادرتها** في التقارير، والتنبيه يتبع يوم **عودتها**؛ تعبئات المازوت تتبع يوم التعبئة التشغيلي.
المجاميع تخص الفترة المحدّدة فقط.

**قاعدة التنبيه** بلا تغيير: لكل زبون، رحلة تتجاوز متوسط مدّته/مسافته بالنسبة المحدّدة (الافتراضي 20%)، بشرط
وجود رحلتين مكتملتين على الأقل. المتوسط يُحسب على رحلات الزبون **حتى نهاية الفترة المطلوبة** ضمن نافذة
`windowDays` (120 يومًا) قبل بدايتها — فيبقى تنبيه يوم سابق مطابقًا لما كان سيظهر وقتها، ولا يتغيّر بتغيّر ما يُحمَّل.
أول رحلة لآلية سُجّلت قبل بداية هذه النافذة تظهر مسافتها «غير متاحة» بدل رقم مضلِّل.

- **لا تغيير على قاعدة البيانات**: لا جداول ولا أعمدة جديدة؛ دالتا قراءة جديدتان فقط (`listEntriesRange`، `listFuelFillsRange`)
  في المحرّكات الثلاثة، والمسار للقراءة فقط وبصلاحية الأدمن/مدير الآليات حصرًا. أقصى طول للفترة 400 يوم.
- المنطق في `reports-core.js` (دوال نقية) ويُختبر في `test/reports.test.js`.

## العمل أثناء انقطاع الشبكة

شبكة البوابة قد تنقطع لدقيقة، والشاحنة لا تنتظر. لذلك **لا يفشل التسجيل عند
انقطاع الاتصال**: يُحفظ في المتصفح ويُرسَل تلقائيًا عند عودة الشبكة.

ما يراه الحارس:

- الشارة في الأعلى تتحوّل إلى **«٣ بانتظار الإرسال»** بدل «متصل ✓»
- العملية تظهر فورًا في قائمة «آليات في الخارج» بشارة **«بانتظار الإرسال»**
  وخط جانبي بنفسجي
- يستطيع تسجيل عودتها وهو ما زال مقطوعًا — تصطفّ العودة خلف مغادرتها
- عند عودة الشبكة يُرفع كل شيء بالترتيب وتختفي الشارة بلا أي تدخّل

القيود مفروضة محليًا أيضًا: محاولة إخراج آلية مسجّلة في الخارج تُرفض حتى
والشبكة مقطوعة، فلا تصل إلى الخادم رحلة مكررة أصلًا.

### لماذا لا تتكرّر السجلات عند إعادة الإرسال

الخطر الحقيقي ليس فشل الطلب، بل **نجاحه وضياع رده**: الخادم يسجّل الرحلة ثم
تنقطع الشبكة قبل وصول التأكيد، فيُعيد الجهاز الإرسال — فتنشأ رحلتان لشاحنة واحدة.

لذلك يولّد جهاز البوابة **مفتاح تعريف** لكل عملية ويرسله معها. الخادم يحفظه
تحت فهرس فريد، وعند رؤية المفتاح نفسه مرة أخرى يُرجع السجل الأصلي بدل إنشاء
سجل جديد. يشمل ذلك حالة السباق: ثلاثة طلبات متزامنة بنفس المفتاح تُنتج صفًّا
واحدًا وتنجح الثلاثة.

`test/idempotency.test.js` يغطي هذا في 16 حالة.

> ملاحظة: البيانات المعلّقة تعيش في متصفح جهاز البوابة (`localStorage`).
> مسح بيانات المتصفح قبل عودة الشبكة يفقدها. لا تمسحها ما دامت الشارة تعرض
> عمليات بانتظار الإرسال.

## قواعد يفرضها الخادم

| القاعدة | ماذا تمنع |
|---|---|
| لا يمكن خروج آلية هي أصلًا في الخارج | صفَّان مفتوحان لنفس الآلية عند استخدام جهازين على البوابة |
| لا يمكن تسجيل عودة مرتين | جهازان يسجّلان عودة واحدة فيكتب أحدهما فوق الآخر |
| كيلومتراج العودة لا يقل عن آخر قراءة | خطأ إدخال يقلب حساب المسافة إلى رقم سالب (يمكن تجاوزه بتأكيد صريح عند تبديل عدّاد) |
| الآلية يجب أن تكون مسجّلة قبل خروجها | رحلة أولى بلا كيلومتراج بداية = مسافة غير قابلة للحساب |
| إعادة تسمية آلية تُحدّث كل سجلاتها | انفصال تاريخ الآلية عن اسمها الجديد |
| لا يمكن حذف آلية في الخارج الآن | عملية معلّقة بلا آلية |

كل حذف أو تعديل أو تغيير كلمة مرور يُسجَّل في **سجل التدقيق** مع الوقت والحساب
وعنوان الجهاز — يراه المدير في تبويب «الإعدادات».

## الاختبارات

مع تشغيل الخادم على المنفذ 8899:

```bash
node test/api.test.js <كلمة-مرور-البوابة> <كلمة-مرور-المدير>
```

```bash
node test/concurrency.test.js <كلمة-مرور-المدير>
```

```bash
node test/idempotency.test.js <كلمة-مرور-المدير>
```

ولا يحتاجان قاعدة بيانات:

```bash
node test/drivers.test.js
```

```bash
node test/verify-mssql.js
```

`drivers.test.js` يتأكّد أن المحرّكات الثلاثة تقدّم واجهة متطابقة (32 دالة،
نفس عدد المعاملات، وتجزئة كلمة مرور يقبلها أي محرّك آخر) — يكشف فورًا أي
دالة نُسيت في محرّك، بدل أن تنكشف عطلًا بعد النشر.
`verify-mssql.js` يفحص جاهزية SQL Server خطوة خطوة قبل التشغيل: الاتصال،
الصلاحيات، إنشاء الجداول، دعم الفهرس المُرشَّح، تخزين العربية، ومنع الازدواج.

`roles.test.js` يتحقّق من دور «منسق حركة الآليات» وصلاحية «تعديل السجل الكامل»: مصفوفة الصلاحيات لكل الأدوار،
تسجيل الدخول والجلسة، إنشاء المستخدم وتعديل دوره، التعديل والتدقيق، ومنع المنسق من التعديل في الخادم: `node test/roles.test.js`.

`guest-stats.test.js` يتحقّق من إحصاءات الزبائن/الضيوف: التسجيل من حسابَي بوابة، مجموع الأدمن، عدم العدّ المزدوج، الصلاحيات، وسلوك قاعدة قديمة بلا العمود: `node test/guest-stats.test.js`.

`reports.test.js` يتحقّق من تقارير الفترة: وحدات `reports-core.js` (حدود 03:00، السلسلة، خط الأساس، عدم التكرار،
تطابق مع منطق الصفحة) ثم خادمًا فعليًا على SQLite مؤقتة مملوءة عبر الـ API: اليوم الحالي، يوم سابق، نطاق،
رحلة تعبر 03:00، الفترة الفارغة، التحقق من المدخلات والصلاحيات: `node test/reports.test.js`.

`opday.test.js` يتحقّق من اليوم التشغيلي (حدود 03:00، الرحلات العابرة، عدّادات أنواع الآليات،
وعدم تغيّر السجلات) ومن أن `/api/state` يرسل `dayStartHour`؛ لا يحتاج قاعدة بيانات
(يشغّل الخادم على SQLite مؤقتة): `node test/opday.test.js`.

`api.test.js` يغطي المصادقة والصلاحيات والتحقق من المدخلات وكل قواعد العمل
(50 حالة). `concurrency.test.js` يرسل طلبات متزامنة فعليًا ليتحقّق أن جهازين
على البوابة لا ينتجان صفوفًا مكررة. `idempotency.test.js` يتحقّق أن إعادة
الإرسال بعد انقطاع الشبكة لا تُنشئ سجلات مكررة (16 حالة).

> `api.test.js` يغيّر كلمة مرور البوابة أثناء عمله، فشغّله على قاعدة نظيفة
> أو أعد استخدام الكلمة الجديدة `bawaba-jadida-77` في التشغيل التالي.

> ملاحظة: حالة «‏CSV يبدأ بعلامة BOM» تظهر فاشلة في `api.test.js` لأن
> `res.text()` في Node يحذف علامة BOM حسب المواصفة. الفحص على مستوى البايت في
> `concurrency.test.js` يؤكّد وجودها.

## النشر على سيرفر الشركة (Windows Server)

1. انسخ المجلد كاملًا إلى السيرفر، مثلًا `C:\GateLog`
2. ثبّت Node.js 24 LTS، وجهّز قاعدة البيانات حسب [SQLSERVER-SETUP.md](deploy/SQLSERVER-SETUP.md)
3. افتح PowerShell **كمسؤول**:

```powershell
cd C:\GateLog\deploy
.\install-windows.ps1
```

السكربت يتحقّق من Node وقاعدة البيانات، ينفّذ `npm install` إن لزم، ينشئ مهمة مجدولة
تعمل عند إقلاع السيرفر وتُعيد تشغيل نفسها إذا توقفت، ويفتح المنفذ 8787 لشبكة
الشركة (Domain و Private فقط)، ثم يطبع الروابط التي تُفتح من أجهزة البوابة.

تفاصيل ما يحتاجه قسم تقنية المعلومات في [deploy/IT-REQUEST.md](deploy/IT-REQUEST.md).

**إن كان الإنترنت ممنوعًا على السيرفر:** نفّذ `npm install` على جهاز آخر وانسخ
مجلد `node_modules` معك. التطبيق بعدها لا يحتاج الإنترنت إطلاقًا.

## النسخ الاحتياطي والاستعادة

**تلقائي:** لقطة JSON كل 24 ساعة في `data/backups`، ويُحتفظ بآخر 60.
**يدوي:** من تبويب «الإعدادات» → «إنشاء نسخة الآن».

هذه اللقطات تكفي لاستعادة بيانات التطبيق، لكن **النسخ الاحتياطي الرسمي يجب أن
يعتمد على `mongodump`**:

```bash
mongodump --db gate_log --out C:\Backups\gatelog
```

```bash
mongorestore --db gate_log C:\Backups\gatelog\gate_log
```

**تصدير للمحاسبة:** تبويب «السجل الكامل» → «تصدير Excel (CSV)». الملف بترميز
UTF-8 مع علامة BOM، فتظهر العربية في Excel بشكل صحيح مباشرة.

## الإعدادات

تُضبط من ملف `gatelog.config.json` (انسخه من `gatelog.config.example.json`)
أو من متغيّرات البيئة. **متغيّر البيئة يتقدّم على الملف عند التعارض.**

رابط Atlas يحتوي كلمة المرور، لذا ضعه في الملف لا في سطر الأوامر — في سطر
الأوامر يظهر لأي مستخدم على السيرفر عبر Task Manager. ثم قيّد صلاحيات الملف:

```powershell
icacls gatelog.config.json /inheritance:r /grant:r "SYSTEM:(R)" "Administrators:(F)"
```

| المفتاح في الملف | متغيّر البيئة | الافتراضي | الوظيفة |
|---|---|---|---|
| `mongoUri` | `MONGODB_URI` | `mongodb://127.0.0.1:27017` | عنوان MongoDB (محلي أو Atlas) |
| `mongoDb` | `MONGODB_DB` | `gate_log` | اسم قاعدة البيانات |
| `driver` | `GATE_LOG_DB` | `mongo` | المحرّك: `mongo` أو `sqlite` |
| `port` | `PORT` | `8787` | منفذ الاستماع |
| `host` | `HOST` | `0.0.0.0` | ضعه `127.0.0.1` لقصر الوصول على السيرفر نفسه |
| `dataDir` | `GATE_LOG_DATA` | `./data` | مسار مجلد النسخ الاحتياطية |
| `windowDays` | `GATE_LOG_WINDOW_DAYS` | `120` | أيام العمليات المكتملة المُرسَلة للواجهة |
| `dayStartHour` | `GATE_LOG_DAY_START_HOUR` | `3` | ساعة بداية اليوم التشغيلي (0–23) |

## ملاحظات

- **الخط:** الصفحة تستورد خط Cairo من Google Fonts. على سيرفر بلا إنترنت يفشل
  هذا الطلب بصمت ويعود التطبيق إلى خط النظام — كل شيء يعمل، يتغيّر الشكل فقط.
- **التشفير:** التطبيق يعمل على HTTP. داخل شبكة محلية مغلقة هذا معتاد، ولو
  فرضت سياسة الشركة HTTPS فالحل هو IIS كوسيط عكسي أمامه بشهادة داخلية، بلا أي
  تعديل على التطبيق.
- **مصادقة MongoDB:** الإعداد الافتراضي لـ MongoDB المحلي بلا مستخدم ولا كلمة
  مرور. يُفضَّل تفعيل المصادقة وحصر المنفذ 27017 على السيرفر نفسه.
- **حجم الاستجابة:** الواجهة تجلب العمليات المكتملة لآخر 120 يومًا فقط، أما
  الآليات التي في الخارج فتُجلب دائمًا مهما قدُم تاريخها. المدة قابلة للتغيير
  عبر `DEFAULT_WINDOW_DAYS` في `server.js`.
